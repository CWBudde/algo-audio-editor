# Public web demo

[Try algo-audio-editor](https://cwbudde.github.io/algo-audio-editor/).
The site follows **main**, after its CI push run succeeds, and is visibly labeled
**Development build**. It is not a stable release. Audio files and processing
stay on your device. The app fetches its own code and the optional bundled demo;
it does not upload your audio. As with other Pages sites, GitHub receives hosting
requests; see [GitHub's Pages privacy information](https://docs.github.com/en/pages/getting-started-with-github-pages/what-is-github-pages#data-collection).

Open a local audio file or choose **Open demo**. The CC0 demo is four seconds of
quiet stereo tones (440/660 Hz, 48 kHz, 16-bit); it is generated by Go and the
tagged upstream DSP/WAV libraries with `just demo`. Playback starts only after
you press Play. Save/Export writes to a selected local destination or hands a
download to the browser. Keep originals: project files and crash recovery are
still planned.

## Deployment and verification

The repository's Pages source is **GitHub Actions**, over HTTPS at
`https://cwbudde.github.io/algo-audio-editor/`. The `github-pages` environment
allows the `main` branch. These settings were confirmed through the GitHub API
on 2026-10-04; existing deploy run 37218337572 succeeded for `e8a373a`.

`.github/workflows/pages.yml` waits for successful CI on a push to main, then
checks out exactly that run's `head_sha` with full history. A manual dispatch
requires successful CI for the dispatched commit. Shared setup pins Bun 1.4.2
and Node 24. The build sets `VITE_BASE=/<repo>/`, stamps the kernel with
`git describe` and a UTC timestamp, and records the full commit in the frontend.
Help → About shows the version, commit, UTC build time and development channel.

After `deploy-pages`, `pages-smoke.yml` visits the deployed URL in new browser
contexts. It checks the expected build commit, isolation/service-worker scope,
local WAV import, real worklet playback with zero underruns, exact saved PCM,
demo loading, warm visits, deep links and blocked-service-worker guidance.
It also runs daily at 07:23 UTC and supports manual dispatch. Failures retain
Playwright traces. A smoke failure fails the workflow; it does not roll back
an already deployed site.

```sh
just e2e-pages
PLAYWRIGHT_BASE_URL=https://cwbudde.github.io/algo-audio-editor/ just e2e-pages-live
```

The local recipe builds into separate `dist-pages` under `/algo-audio-editor/`
(leaving the root-path browser/Electron build intact) and uses `serve-pages.mjs`,
which sends gzip responses and **no isolation headers**. This reproduces the
service-worker boot rather than relying on Vite's COOP/COEP headers. These tests
run in CI and `just ci`. `PLAYWRIGHT_BASE_URL` must end with `/`; the live recipe
does not build or launch a server. Regular Playwright configuration also accepts
this variable, but existing root-relative specs are not the Pages acceptance suite.

Vite copies the processed `index.html` to `404.html`. Deep links boot the same
editor with absolute subpath assets; unknown routes still have HTTP status 404
and do not represent saved document links.

## Isolation and caches

Playback needs SharedArrayBuffer and [cross-origin isolation](https://developer.mozilla.org/en-US/docs/Web/API/Window/crossOriginIsolated).
Pages cannot set this app's COOP/COEP headers. The adapted MIT
`coi-serviceworker.js` adds `same-origin` COOP and `require-corp` COEP to fetched
responses. It registers with explicit repository scope and `updateViaCache: none`.
A cold visit reloads once after a controller is available; a session-storage
guard prevents a reload loop. If registration, secure-context support or session
storage is blocked, the editor presents isolation guidance. Allow service workers,
try a regular current-browser window, or use the desktop app.

The worker keeps **no CacheStorage or offline application cache**. Controlled
HTML navigations fetch with `cache: no-store` and return `Cache-Control: no-store`.
Its initial script reference carries a content-hash query. Vite bundles JS/CSS
with hashes and copies the kernel, the speech worker's `speech.wasm` and the
matching Go runtime to independent SHA-256 filenames. Unversioned
`kernel.wasm`/`speech.wasm`/`wasm_exec.js` are removed from the published build.
The speech program loads only when **Generate speech…** is used; its model files
come from pinned Hugging Face URLs and are verified by SHA-256 in the browser. Updated header-only workers can activate without reloading an
editing session; existing tabs keep their instantiated kernel. Reloading starts
a fresh session and can lose unsaved work.

**Hosting limitation:** GitHub's CDN controls the first HTML/script response
and asset cache lifetime (the observed live responses use `max-age=600`). A
service worker cannot override those first-response CDN headers or guarantee
long-term immutable caching. The strict original “never cached HTML/worker,
long-term assets” roadmap gate remains open. Content hashes prevent a cached
old kernel from being used under a new kernel URL; a stale CDN HTML response can
still reference assets removed by a later deployment. Post-deploy commit
verification and CI retries detect propagation failures, rather than claiming
atomic CDN updates. No offline/PWA support is promised.

## Size budget

Every `just build` runs the pinned Binaryen 132.0.0 `wasm-opt -Oz` after Go's
`-trimpath -s -w` build, then builds Vite's production artifacts and runs
`check-web-budget.mjs`. Go's bulk-memory, nontrapping conversion and sign-extension
features remain enabled; IEEE/trapping semantics are preserved. The optimizer is
installed by `bun install`, including on Windows and CI.

The checker measures gzip level 9 and fails closed if the content-hashed kernel,
the content-hashed speech program or the module entry is missing. Browser CI explicitly repeats this gate after e2e.
It includes **all** JS files, including lazy dialogs, worker and Go runtime:

| Artifact | Limit |
| --- | --- |
| WASM, raw | 12 MiB |
| WASM, gzip | 3 MiB |
| Speech WASM, raw | 8 MiB |
| Speech WASM, gzip | 2.5 MiB |
| Any JS chunk, raw | 500 KiB |
| Entry JS chunk, gzip | 160 KiB |
| All JS artifacts combined, gzip | 384 KiB |

Dialogs and effect controls load on demand. React's shared runtime has its own
cacheable chunk. The existing Vite kernel/runtime content hashes are computed
from the final optimized bytes. Build logs and GitHub summaries record measured
sizes and budgets; the download limits remain separate from kernel memory limits.

## Browser support

Use a current desktop browser with WebAssembly, module workers, AudioWorklet,
SharedArrayBuffer and service workers enabled. This is a feature/support matrix,
not a claim of full automated acceptance on every engine.

| Browser | Editor and isolation | Files and codecs | Verification |
| --- | --- | --- | --- |
| Chromium (Chrome/Edge) | Reference browser; Pages worker enables isolation. Extensions/private-mode policies may block it. | Portable Go WAV/FLAC/AIFF/MP3. File System Access where available, otherwise download/input. Browser decode and WebCodecs export are checked at runtime; Linux AAC encoding is unavailable. | Automated Chromium local, headerless subpath and live WAV smoke. |
| Firefox | Requires the same isolation features; private mode or policy can disable service workers. Visible guidance when blocked. | Portable Go codecs; file input/download fallback. Ogg/AAC decoding and Opus/AAC encoding depend on exposed browser/OS APIs; unsupported exports are disabled. | Full editor and deployed-site acceptance pending. |
| Safari (macOS) | Requires modern WebAssembly/worker/AudioWorklet/isolation support; storage and service-worker restrictions can prevent Pages isolation. | Portable Go codecs; file input/download fallback. Browser codec support and native AAC encoder quality still need acceptance on macOS. | Full editor and deployed-site acceptance pending. |

Browser codecs do not imply identical frame counts or gapless exports across
engines. See [codec details and limits](codecs.md),
[decodeAudioData](https://developer.mozilla.org/en-US/docs/Web/API/BaseAudioContext/decodeAudioData)
and the [WebCodecs specification](https://www.w3.org/TR/webcodecs/), which does not
require particular codecs. Mobile/touch acceptance is not part of this matrix.
